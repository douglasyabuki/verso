# Presentation components

- Keep presentation in `components/`, interaction hooks in `hooks/`, workflow coordination in `contexts/`, observable state and persistence in `stores/`, and pure domain rules in `lib/`. Keep component-specific props and private implementation types beside their components.
- Reserve `components/ui/` for shadcn components and reusable primitive-level components. Change their shared styles or behavior only when the change should apply across the application. For a feature-specific or single-consumer adjustment, prefer styling or composition in the consumer; keep feature-specific wrappers outside `ui/`.
- Preserve existing Base UI primitives and accessible interactions. Use existing component variants before introducing consumer overrides, and add shared variants only for application-wide conventions. Load the root shadcn skill for applicable component work.
- Use the shared helpers in [ui/disclosure.tsx](ui/disclosure.tsx) for new or modified content disclosures. Keep expansion state with its existing owner and preserve the primitives in [ui/collapsible.tsx](ui/collapsible.tsx).
- Order disclosure trigger children as `DisclosureChevron`, optional decorative icon or language flag, `DisclosureLabel`, and optional count. Keep the chevron a direct child of the actual trigger button. Counts may sit inside the label when they should wrap with it.
- Apply `disclosureTriggerClassName` to ordinary triggers. Preserve the appropriate minimum height with `cn`: `min-h-8` for default buttons and `min-h-6 py-0.5` for `xs`; the shared style already covers `sm`. Keep the 8px gap, wrapping label, and non-shrinking leading decoration. Do not restore fixed heights, `whitespace-nowrap`, or trigger-level `flex-wrap`.
- Let `DisclosureChevron` own its fixed `size-4 shrink-0`, muted color, 200ms rotation transition, and reduced-motion behavior. Its explicit size excludes it from Button's `svg:not([class*='size-'])` rules, including `xs` and `sm`. Do not add caller sizing overrides or parent selectors that resize it.
- For custom disclosure layouts or separate expansion buttons, use `disclosureChevronTriggerClassName` and the shared chevron. Rotation must depend on the owning button's `aria-expanded`, never an ancestor group's expansion state. Use a 16px chevron column and 8px gap in custom text-trigger layouts.
- Use `DisclosureGuide` inside inline disclosure content, or apply `disclosureGuideClassName` directly to an existing field container. Preserve one 1px semantic start border, 16px start margin, 16px start padding, 12px top spacing, and automatic width to accommodate the margin. Replace old guide and spacing classes instead of stacking guides; retain shaded reference boxes inside the guide. Use logical start/end properties.
- Keep Issues and both PDF technical-details panels separated by their existing boundaries without an extra guide. Preserve the sidebar's navigation hierarchy and separate expansion button; its single logical-start guide may retain navigation-specific spacing.
- Use semantic buttons, visible keyboard focus, accurate expanded/control relationships, and decorative icons hidden from assistive technology. Keep other actions outside disclosure triggers. Preserve controlled/uncontrolled state, default-open behavior, mounting and `keepMounted`, validation-driven expansion, draft flushing, issue navigation, focus targets, and scrolling.
- Keep menus, selects, breadcrumb chevrons, and sidebar/preview visibility controls outside the content-disclosure convention.
- When changing disclosures, inspect expanded/collapsed states, nested disclosures, long labels, narrow layouts, keyboard operation, and reduced motion where UI tooling is available. Confirm 16px by 16px chevrons across Button sizes and custom/sidebar triggers. Follow root validation instructions and report unavailable checks.
- Leave a blank line after imports and between declarations. Follow the repository formatter and import sorting rules.
